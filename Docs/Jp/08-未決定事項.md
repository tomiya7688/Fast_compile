# 8. 未決定事項

現時点で大きく未決定または実装前に確定が必要な項目:

- 演算子優先順位の残り: ビット演算・シフト演算の位置、比較と等価の相互順位の細部、および一般的なオペランド評価順序。
- Windows x86-64 のobject/executable format詳細と既定linker。
- Windows toolchain integration。
- C-compatible struct layoutの明示構文。
- C++ wrapper/adaptor toolの具体仕様。
- 標準libraryの最小セットとpackage構成。
- 軽量backendのx86-64 register allocation・calling convention loweringの詳細。
- 独自optimizerのpass順序とbudget。
- compiler binary / CLI名、build profile名。
- formatter (`fc fmt` 相当) の具体仕様。
- test/build/package managementのCLIとproject manifest。

表面構文はかなり固まっているが、parser実装開始後に矛盾が見つかった場合は日本語正本を更新してから実装へ反映する。

## 設計レビューに基づく推奨事項（2026-11-06）

外部レビューを踏まえ、コア原則（コンパイル速度最優先・局所判定・GCなし・miscompile回避）を崩さない範囲で、以下を推奨する。これらはまだ「決定」ではなく、実装前に優先して確定・文書化すべき候補である。決定したら該当章へ正式反映し、本節から移すか削除する。

### 1. 演算子優先順位の早期確定（最優先）

未決定のビット演算・シフト・比較/等価の相互順位は、Lexer/Parser実装の前に確定する。

**推奨案（C系に近く、学習コストを抑える）:**

| 優先順位（高い順） | 演算子 |
|---|---|
| 最優先 | `(...)` |
| 高 | 単項 `! ~ + -` |
| 次 | `* / %` |
| 次 | `+ -` |
| 次 | `<< >>` |
| 次 | `< <= > >=` |
| 次 | `== !=` |
| 次 | `&` |
| 次 | `^` |
| 次 | `\|` |
| 次 | `&&` |
| 低 | `\|\|` |

同一優先順位は左結合。オペランド評価順序は原則左から右とし、副作用のある式の評価順を文書化する。

理由: パーサの複雑さを増やさず、既存言語経験者の直感に合う。決定後は `03-言語コア.md` の表を更新する。

### 2. string の mutation と性能

現仕様の16byte固定表現（pointer + tagged length、capacityなし）は正しい。ただし「頻繁に追記する」用途では再確保がコストになる。

**推奨:**
- 言語仕様として capacity を持たせない方針は維持する。
- 標準libraryに `StringBuilder`（または `array<byte>` を使った明示的な構築パターン）を最小セットに含めることを検討する。
- 診断やドキュメントで「stringはimmutable・追記はBuilderかarray経由」を明示する。

### 3. Result の使いやすさ（言語機能は増やさない）

`?` や try を入れない方針は維持する（コンパイル量と解析を増やさないため）。

**推奨:**
- 標準libraryに `unwrap` / `unwrap_or` / `map` 相当の薄いヘルパを用意する方向を検討する。
- 早期returnパターンを推奨する文書を `03` または標準library設計に書く。
- 深いネストを強制しない書き方の例を公式サンプルに含める。

### 4. import と型依存の診断品質

「型名を明示する／field・methodを使う場合は定義元packageのimport必須」ルールはコンパイル速度に寄与する良い設計である。

**推奨:**
- 診断メッセージを具体的にする。「`models.user::User` のfieldにアクセスするには `import models;` が必要です」のように、必要なimportを直接示す。
- 推論だけで値を受け渡しする場合はimport不要である点を、エラー例と対比して文書化する。

### 5. opaque generic の type descriptor 最小集合

user-defined genericsで `T` をopaqueに扱う方針は正しい。

**推奨する最小descriptor（実装前に確定）:**
- size / alignment
- drop（所有値の場合）
- move
- copy（Copy型の場合のみ）
- 必要なら zeroing や default の有無

任意の `+` やmethodを仮定しない現方針を維持し、descriptor経由で必要な操作だけを許す。

### 6. 大きな move-only 値の更新パターン

可変借用を持たないため、更新は `x = f(move x);` になる。これは意図的である。

**推奨:**
- 言語としては可変借用を追加しない。
- コンパイラは「同一変数への即時再代入」の典型パターンを、aliasが存在しない範囲で効率的なコードに落とし込める余地をbackend側に残す（as-if ruleの範囲）。
- 標準libraryでよくある更新パターン用の薄いヘルパを検討する（言語機能ではない）。

### 7. 実装フェーズの明示

現在は「C製bootstrap（入力読み込み・CLI）」段階である。

**推奨:**
- 設計原則または本節に、おおよそのフェーズを書く。
  1. Bootstrap: source load / CLI / 最小Lexer・Parser
  2. 型検査・所有権チェック（単一file）
  3. interface metadata と incremental の骨格
  4. 軽量backend（x86-64）
  5. 独自optimizer / LLVM任意backend
- 各フェーズで「何を捨てているか」「何を保証するか」を明確にし、Issue分割の指針にする。

### 8. その他の小さな推奨

- **CLI名**: 開発用 `fastc` を当面維持し、正式名決定時に互換エイリアスを検討する。
- **差分テスト**: 軽量版と独自最適化版（および可能ならLLVM）の differential test を早期から必須化する方針を `06` に明記済みなので、Issue側でテスト基盤を優先する。
- **未初期化禁止**: module-levelも含めて厳格に守る現方針は良い。初期化式のcompile-time評価範囲を小さく保つ。

これらの推奨はコア原則に反しない範囲での改善案である。採否は仕様決定プロセスに従い、日本語正本を更新したうえで実装Issueを分割する。
