# 1. 設計目標・原則

## 最優先目標

Fast compile は **大規模プロジェクトの総ビルド時間を短くする** ための言語である。

小規模プロジェクトの数秒を削ることにも意味はあるが、主戦場は数十分〜数時間かかるビルドである。

成熟版の合格条件は、代表的なベンチマークで以下を満たすこと。

- C++を大幅に上回るビルド速度。
- Goより速い incremental build。
- Goより速い clean build。

測定対象は少なくとも startup、単一ファイル、clean build、1関数変更、public interface変更、link時間、CPU時間、peak memory、再処理コード量を分ける。

## 正しさもビルド性能

速くコンパイルできても、miscompile・クラッシュ・不正キャッシュ・分かりにくい診断で再ビルドが増えれば意味がない。

- 同じ入力は決定的な出力を生成する。
- incremental cacheは安全側に倒す。
- optimizerが壊れたIRを生成したら実行ファイルを出さない。
- 軽量backend、独自最適化backend、必要に応じLLVMで差分テストする。

> 最速のビルドとは、最初の1回で正しい成果物が得られるビルドである。

## コンパイラが考える量を減らす

Fast compile は構文とmetadataから答えが直接分かる場合、候補探索や全体推論を行わない。

意図的に避けるもの:

- 関数overload候補探索
- 暗黙数値変換探索
- user-defined operator探索
- transitive import
- macro展開
- 任意のcompile-time実行
- C++ template型の型ごとの本文再コンパイル
- cross-function lifetime推論
- mutable borrow alias解析
- virtual dispatch用の実行時探索
- hidden module initialization

## 実行速度・ランタイム

Fast compile は「コンパイルだけ速いが実行は遅い」言語を目指さない。

- ネイティブコード生成。
- GCなし。
- 例外unwindなし。
- VMなし。
- 必須のvirtual object runtimeなし。
- 必須async executorなし。
- 通常ビルドでも十分高速なコード生成。
- より強い最適化が必要な場合は独自最適化版またはLLVMを選べる。

ランタイムは小さくし、使わない機能をリンクさせない。大規模なソースツリーだからといって常駐ランタイムが巨大になる設計は禁止する。

## コンパイラ本体

コンパイラ本体も必要以上に巨大化させない。ただしコード量削減のために可読性や正しさを犠牲にはしない。

## Issue運用と実装順

仕様として決定した内容は、実装済みでない限り、実際に実装できる単位へ分割してGitHub Issueへ登録する。

Issueは依存関係を考慮し、実装する順番が分かるように並べる。

原則:

- 決定済み仕様を未実装のままIssueなしで放置しない。
- 1 Issueはレビュー可能な実装単位にする。
- 後続Issueは必要な先行Issueを明記する。
- 仕様が未決定の部分を推測で実装Issueにしない。
- 実装が日本語正本の仕様と異なることが判明した場合、その差異は**修正Issueとして別途起票する**。
- 仕様不一致を見つけた場合、Issueを作らずに「ついで修正」で隠さない。
- 修正Issueには、正しい仕様、現在の誤実装、影響範囲、回帰testを明記する。
- 仕様そのものを変更する場合は、先に日本語正本を更新し、その後に実装Issueを更新または追加する。

> 仕様決定はIssueへ落とし、仕様不一致は修正Issueとして追跡する。
